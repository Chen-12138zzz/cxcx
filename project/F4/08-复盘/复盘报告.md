## 0. 复盘纪律

本复盘**不做**以下三件事：

| 不做 | 理由 |
|---|---|
| ❌ 不做"我们很努力"式的过程陈述 | 过程努力不构成可复用的知识 |
| ❌ 不做"下次注意"式的表层总结 | "注意"不是可执行动作，不改变下次的结果 |
| ❌ 不掩盖失败 | 失败留下的信息量大于成功 |

本复盘**只做**一件事：**找出哪些结构性的东西，如果不改，下次一定还会出错。**

## 2. 根因分析

### 2.1 根因一：**"算对了"和"问对了"是两件事，而后者不会被报错捕获**

#### 现象

B 类判据设计错误共 5 条，**代码全部正确**：

| 编号 | 表面现象 | 真实问题 |
|---|---|---|
| B-1 | 方差分解不闭合 | 把"方差可加"当**无条件恒等式**（实际只在分量独立时成立） |
| B-2 | 谱能量占比只有 27% | 把"特征尺度"等同于"能量峰值波长" |
| B-3 | 阈值对从不共现 | 用**两个绝对阈值**表达一个**相对关系** |
| B-4 | `100m→True` 与预期不符 | 心算尺度（"100 和 50 差不多"） |
| B-5 | NMSE 说融合有害 | **问错了量** —— 用未标定的误差判断质量 |

#### 根因

**软件工程有编译器、有异常、有测试失败来捕获"算错"。
但没有任何机制捕获"问错"。**

一个判据写错时：

1. 它**不会**抛出异常（因为语法与类型都对）；
2. 它**不会**失败（因为它算出了一个数）；
3. 它**看起来很像真的**（因为它是用正确的方法算出来的一个数）；
4. 它甚至会**看起来更可信** —— 因为它带着浮点小数位。

⇒ **判据错误的信噪比远低于实现缺陷**：实现缺陷会"响"，判据错误只会"静默地正确"。

#### 为什么这在本项目里特别危险

本项目的**产出就是判据**。一个实现缺陷只影响一个函数；
一个判据错误会影响**整个结论的方向**。

B-5 就是实例：代码没错，但它给出的答案是"融合有害"，
与真相**符号相反**。

#### 可执行的对策（不是"下次注意"）

| 对策 | 具体做法 |
|---|---|
| **C-1 零假设自检** | 每条判据必须回答："在应当**无效应**的输入上，它报什么？"<br>实例：`f=1` 时保留率必须**恰为** 1（tests C9） |
| **C-2 恒不通过自检** | 问："这个诊断有没有可能**永远不通过**？"<br>实例：`audit_summary` 在缺 `rel_sd=0` 基线时**必须**报 `ok=False`（tests E13） |
| **C-3 退化情形自检** | 每个函数必须回答："退化输入下应报什么？"<br>实例：常数层必须被 `assert_not_degenerate` 拒绝 |
| **C-4 跨种子验证** | 单种子结论**不得**写成"总是成立"<br>实例：B-3 修正后跨 12 种子验证，才发现 f=16 只有 5/12 |
| **C-5 追问"这个量在问什么"** | 每当一个数字支持某个结论时，反问："还有哪个量会给出不同答案？"<br>实例：B-5 之后加入了 G4b（符号反转断言） |

> **C-5 是本次复盘得出的最深一条**：
> **一个数字能支持结论，不等于它问对了问题。**
> 发现 B-5 的方式正是追问"如果换一个指标，结论会不会翻"——
> 结果换了 `pearson_r` 后符号确实翻了。

### 2.2 根因二：**"代码↔文档"的一致性没有任何自动检查**

#### 现象

A-6、A-7 两条接口缺陷**没有被任何测试捕获**：

| 编号 | 问题 | 为什么没被发现 |
|---|---|---|
| A-6 | `synth`/`mce` 缺 `__all__` | 没有测试依赖 `__all__` |
| A-7 | 注解 `-> np.ndarray` 但实返回 `dict` | **类型注解不参与运行** |

发现它们的方式是**写接口文档时用脚本抽取签名**。

#### 根因

`consistency_check.py` 只做**文档之间**的校验（禁用值、权威值、绝对化表述）。
**"代码签名 ↔ 文档"之间没有任何校验通道。**

于是产生了一个**单向失效**：

```
代码改了  →  文档不改  →  无任何报错  →  文档变成谎言
```

而**文档是给读者看的**。A-7 写的 `-> np.ndarray` 会让读者相信它返回数组 ——
**这比不写注解更糟**。

#### 与 F1 方向的一致性

这与 F1 的观察一致：**"文档类修正也会误导且不报错"**
（路径写错、状态滞后一轮、缺口披露不完整）。
本次又发现了第三类：**注解与实现不符**。

#### 可执行的对策

| 对策 | 具体做法 |
|---|---|
| **C-6 文档中的接口必须机器抽取** | 接口文档的所有签名由 `inspect.signature` 生成，**禁止手工转录** |
| **C-7 接口基线化** | 把"25 个公开符号"作为基线写下；任何偏离即为接口变更 |
| **C-8 覆盖缺口显式登记** | A-6/A-7 **无自动化断言**这一点写进 `修正记录.md` 与接口文档 §7.3，标为 GAP-1 |
| **C-9 状态字段不得预先填写** | 见 2.4 |

### 2.3 根因三：**"分母口径"是最难自察的一类错误**

#### 现象

A-2：`variance_retention` 在 `f=1`（完全不粗化）时返回 **1.022117**。
正确值是 **1.000000**。

#### 为什么这条特别危险

| 特征 | 后果 |
|---|---|
| 只差 0.022 | 落在"看起来像浮点误差"的区间 |
| 方向性偏差 | 它让**整条曲线**的水平偏乐观（f=2 由 0.9052 变成 0.9253） |
| 不报错 | 1.0221 是一个**合法的浮点数** |
| 只在特定输入暴露 | 只有 `f=1` 才暴露，而 `f=1` 恰恰是最"没用"的一档 |

⇒ **如果我们的实验曲线从 f=2 开始，这条缺陷永远不会被发现。**

#### 根因

分子是"**池体像元**聚合值"的方差，分母用了"**全像元**"方差 ——
**两个不同的总体相除**。

这与 F1 方向的 R-2（分子分母不同尺度）是**同一类错误**。

#### 可执行的对策

| 对策 | 具体做法 |
|---|---|
| **C-10 每个比值必须声明分子与分母的总体** | 并在代码里写注释 |
| **C-11 恒等点必须纳入曲线** | `f=1`（无效应点）**必须**在实验范围内 —— 它是唯一能暴露口径错误的输入 |
| **C-12 跨方向复用教训清单** | F1 的 R-2 已记过同类错误，仍在本项目重犯 ⇒ **教训清单需要成为入门检查项，而不是散落在复盘里** |

> **C-12 是这条根因里最值得记的一点**：
> 我们**已经**在 F1 方向记录过"分子分母不同尺度"这类错误，
> 但 F4 仍然重犯了。**说明"记录教训"不等于"避免重犯"** ——
> 教训必须变成**可执行的检查项**（C-10 就是这样一个检查项）。

### 2.4 根因四：**『写给读者看的事实字段』被凭记忆填写**（D-2 与 D-3）

#### 现象

`00-项目管理/项目总览-README.md` §4「交付物清单」在
`02-申报材料/`、`06-成果/`、`07-结题/`、`08-复盘/` **目录还是空的时候**，
就已经把这些行标为"**已完成**"。

#### 根因

这是**计划状态与事实状态混写在同一字段**。

"交付物清单"这张表同时承担了两个职责：

1. **计划**（我打算交什么）；
2. **状态**（我交了什么）。

当状态字段按"计划应当如此"填写时，它就变成了**一个会说谎的字段** ——
而且**不会有任何东西报错**，因为它是 Markdown 表格里的一个字符串。

#### 危害

| 危害 | 说明 |
|---|---|
| 对内的危害 | 任何人（包括自己）读这张表，都会以为工作已完成，**从而不去检查** |
| 对外的危害 | 若此文档被评审看到，等于**虚报完成度** |
| 隐蔽性 | 它不会报错、不会失败。**这正是 F1 复盘里"状态滞后一轮"的同类问题** |

#### 可执行的对策

| 对策 | 具体做法 |
|---|---|
| **C-13 状态字段必须有机械依据** | 状态列的值必须能被**文件存在性检查**验证，不得凭记忆填写 |
| **C-14 计划与状态分表** | "打算交什么"和"已交什么"用两张表，避免一栏两义 |
| **C-15 一致性校验应覆盖状态列** | 把"每个标记为已完成的交付物，其文件必须存在"写成可执行检查 |

> **这条根因最有普适性**：它和 A-7（注解写错）是**同一类错误的两个实例**
> （两者对应 `修正记录.md` 的 A-7 与 D-2）：
> **"写给读者看的信息"如果错了，比"没有这个信息"更糟**，
> 而且两者都**不会被任何自动机制捕获**。

### 2.5 根因五：**做顺手的事，把"能不能交差"推到后面**（结构性）

#### 现象

本项目的时间分配（按实际投入）：

| 工作 | 投入占比（估） | 是否为核心交付 |
|---|---|---|
| 写代码 + 测试 + 实验 | **约 70%** | 是（但**不是唯一**） |
| 写技术文档 | 约 20% | 是 |
| **写申报书/成果/结题的 `【待填】` 字段** | **约 5%** | **是**（**这是真正决定能否交差的**） |
| 复盘与校验 | 约 5% | 是 |

#### 根因

**这是本项目的结构性失败模式，也是本项目最重要的一条结论：**

> **"先把最难（且完全可控）的事做完，把'能不能交差'压到最后。"**

为什么这会发生：

| 机制 | 说明 |
|---|---|
| **可控性偏好** | 写代码的反馈是即时的、确定的、可自测的；写申报书的反馈是延迟的、依赖他人的 |
| **成就感偏好** | 140 条断言全绿带来明确的完成感；填 `【待填】` 不带来任何完成感 |
| **风险错觉** | "代码难所以风险大"—— **实际上代码风险最低**，因为它能被自己验证 |

#### 与《蓝哨》的对照

《蓝哨》的失败根因是"**用文献缺口立项**"。
本项目的失败根因**不同**：不是立论错，而是**把外部依赖压到最后**。

但两者**有共同的深层结构**：**都在逃避那些"不能被自己验证"的环节**。

| | 《蓝哨》 | F4 |
|---|---|---|
| 逃避的环节 | 验证"别人是否已做"（需要检索他人工作） | 落实"外部依赖"（需要他人配合） |
| 逃避的方式 | 换成"我很确定没人做" | 换成"先把代码写好" |
| 结果 | 立论被反例击穿 | 交付物不完整 |

#### 可执行的对策

| 对策 | 具体做法 |
|---|---|
| **C-16 外部依赖必须第一天启动** | 任何需要他人配合的项（现场准入、数据授权、指导教师确认、`【待填】` 字段）在第 1 天列出并**并行**推进，绝不串行到最后 |
| **C-17 每个阶段都必须产出一个"可交差"的版本** | 不允许"最后统一补齐"；每阶段结束时交付物必须是**可直接提交**的状态 |
| **C-18 以"能否交差"而非"是否做完"作为进度主指标** | 代码完成度不是进度；**可提交的交付物数量**才是 |
| **C-19 难点优先 ≠ 价值优先** | 排序依据应是**"不做会不会导致交不了差"**，而不是"难不难" |

> **C-16 是本复盘最应该被下一届直接采用的一条。**
> 它的形式很简单：**项目第 1 天，列出所有"需要别人才能完成"的项，全部启动。**

## 3. 做得对的地方（也要写清为什么对）

| 做法 | 为什么对（不是"感觉好"，而是有机制） |
|---|---|
| **合成场做成"结构已知"而非纯噪声** | 使"融合是否提升精度"这个命题**可被证伪**；纯噪声上任何方法都能"表现更好" |
| **把 `f=1`（无效应点）纳入实验** | 它是唯一能暴露分母口径错误的输入（见 2.3） |
| **`rel_sd=0` 作为曲线必含档** | 提供了"恒通过也是可疑信号"的判据（F1 的 R-13 教训的可执行化） |
| **判据预处理"零假设下应报什么"** | 直接把 B 类错误从"事后发现"变成"事前设计" |
| **修正记录只增不删** | 使"改过什么"可追溯；且保留了**错误的原始表述**，后人能看到错在哪 |
| **红线 G-3 不预设融合方向** | 使 `fusion_hurts` 被如实报告，**从而暴露了符号反转这个核心发现** |
| **接口文档由脚本抽取** | 直接发现了 A-6/A-7 —— 手工转录永远不会发现这两条 |
| **把判据失败转化为主结果（B-5）** | 这是本项目最有价值的一次决策：**没有把失败改掉，而是把它变成发现** |

> **"把判据失败转化为主结果"值得单独强调**：
> 当时的选择是二选一 ——（a）改判据让它通过；（b）承认判据问错了量。
> 选 (b) 之后，`ΔNMSE_raw > 0 而 ΔNMSE_cal < 0` 成了本项目最有力的一条示范。
> **如果选了 (a)，这个发现就不存在了。**

## 5. 结论

### 5.1 三条结构性结论

**结论一：缺陷主要不在"写代码"时暴露，而在"验证"与"文档"时暴露。**

24 条缺陷中只有 5 条（21%）是写 `src/` 时发现的。
⇒ **"写测试""写实验判据""写文档"不是收尾工作，而是主要的质量机制。**

**结论二：判据错误的信噪比远低于实现缺陷，因此必须靠"设计"而非"发现"来控制。**

31 条判据首轮失败 5 条，**5 条全部是判据写错而非代码算错**。
⇒ 判据必须经过 J-1~J-8 八项检查**才能写下去**，不能靠跑出来再说。

**结论三（最重要）：本项目的失败模式是"先把最难且可控的事做完，把'能不能交差'压到最后"。**

这与《蓝哨》的失败模式**形式不同但结构相同**：

| | 《蓝哨》 | F4 |
|---|---|---|
| 逃避的环节 | 验证他人是否已做 | 落实外部依赖 |
| 共同结构 | **都在逃避"不能被自己验证"的环节** | |

⇒ **下一届必须在第 1 天启动所有外部依赖项，并以"可提交的交付物数量"作为进度主指标。**

### 5.2 本项目最值得保留的一件事

**把一次判据失败（B-5）转化为项目最强的结果（符号反转）。**

它示范了一个可复用的决策规则（J-17）：

> **当一条判据失败时，先问"是不是我问错了量"，而不是先改判据。**

因为**判据失败有两种原因**：代码错了，或者判据错了。
第二种情况下，**失败本身就是发现**。
